# CLAUDE.md

**GateSense**: a face-recognition attendance system. An entrance camera records IN time and an exit camera records OUT time for enrolled (known) people only. Unknown faces are ignored.

**Read [PLAN.md](PLAN.md) first.** It is the full design. The decisions below override PLAN.md where they differ.

## Decisions

- Python 3.11. OpenCV for video: webcam now, RTSP IP cameras later.
- Face detection and recognition: InsightFace (SCRFD + ArcFace) with the **buffalo_s** model pack on **onnxruntime, CPU only**. No YOLO. GPU support is optional later.
- No model training. Enroll each person from 5 to 10 photos, turned into 512-d embeddings.
- Match by cosine similarity with a configurable threshold, starting at 0.45.
- CPU speed: process 5 to 10 fps, detect on frames about 640 px wide, recognize only the best few frames per person.
- Full resolution after detection: the worker detects and tracks on the `FRAME_WIDTH` copy (`resize_to_width`), then `detector.scale_detection(det, detection_scale(frame, small))` moves box and landmarks to camera pixels; the quality filter (`MIN_FACE_PX` = camera px), ArcFace alignment and snapshot use the full frame. Tracking, voting, cool-down, the drawn view and the live JPEG stay at detection size. A frame already ≤ 640 px (webcam) isn't resized, so it's the same frame and detection objects as before. Live decisions carry `face_px` (camera px); the probe's median/warning are camera px too.
- Load only the `detection` and `recognition` modules (`allowed_modules`); buffalo_s also ships gender/age and landmark models we don't use.
- Tracking: ByteTrack from **supervision** (MIT), pinned to **0.30.9**, the last release that includes it (0.31 moved it to Roboflow's separate `trackers` package). Not Ultralytics (AGPL).
- Per track: embed only the best `BEST_FRAMES_PER_TRACK` frames; record when one person wins `VOTE_MIN_AGREE` of them.
- One `recognize.py` process per camera (`--camera NAME` from `config.CAMERAS`); direction comes from the camera.
- Cool-down per (person, camera), seeded from the DB on start. For video files, event time = run start + video position.
- Storage: SQLite at `data/attendance.db` (WAL mode for several camera processes). Embeddings stay in `data/gallery.npz` for now. Day = calendar date (shift windows later).
- Dashboard: the React web app (`web/`), served with the FastAPI API (`api/`) as one app. The Streamlit dashboard was retired once React covered all its features (streamlit, streamlit-webrtc, aiortc, av and pandas are gone).
- API (Phase 1, FastAPI): `api/` next to `app/` and the dashboard; `python -m api.run` / `start-debug.bat` serve `api.main:create_app` (factory) on `API_HOST:API_PORT` (127.0.0.1:8000). CORS only for `API_CORS_ORIGINS` (`http://localhost:5173`, Vite), with credentials (the session cookie). `GET /api/health` (version, uptime, database status; 503 if the database can't be read) and `POST /api/auth/login` are the only public endpoints (`api.main.PUBLIC_PATHS`); a test calls every OpenAPI path without a cookie and expects 401. Pinned: fastapi 0.159.1, uvicorn[standard] 0.54.0, pydantic 2.14.1; tests need httpx2 2.16.0 (starlette 1.9's TestClient warns on plain httpx).
- API workers: `api.workers.WorkerManager` wraps `app.workers.WorkerManager` (same recognize.py processes and run-dir files as the dashboard); started in the lifespan (`open()` writes `data/run/_api.json`, a second API is refused) and `close()` stops the workers this API started, in parallel. `start()` raises `CameraBusy` when any process already runs the camera (says who: `held_by` = api / command line / other, from `parent_pid` in the worker status file), when another worker has the same webcam, or while the enrollment wizard holds the webcam (see the web dashboard bullet). Backstop: recognize.py takes OS locks `camera-<name>.lock` and `webcam-<index>.lock` (`workers.acquire_camera`, msvcrt/fcntl; freed by the OS even on a kill) before opening the camera, so simultaneous starts can't both open it. Managers never probe the locks.
- API users (Phase 2): roles admin / hr / viewer / guard and their permissions only in `api/permissions.py` (`ROLE_PERMISSIONS`; some permissions are for later phases). Every endpoint uses `Depends(require_permission("x"))` from `api/auth.py`; denials are audited (`permission_denied`). argon2 (argon2-cffi 25.1.0) hashes; login sets cookie `SESSION_COOKIE` (httpOnly, SameSite=Strict, `Secure` only if `SESSION_COOKIE_SECURE`), token stored as SHA-256 in `sessions`; `SESSION_HOURS` 8 sliding (extended at most every `SESSION_REFRESH_SECONDS`, cookie re-sent). `LOGIN_MAX_FAILURES` 5 wrong passwords lock for `LOGIN_LOCK_MINUTES` 15 (right password refused meanwhile). First start with no users: `admin` from `GATESENSE_ADMIN_PASSWORD` (env or .env; refuses to start without it), `must_change_password` until changed; only `allow_password_change=True` endpoints (me, logout, password) work until then. Admin endpoints `/api/users` (list, create with temporary password, role, deactivate/activate, reset password) need a reason, audit in the same transaction, can't remove the last active admin or deactivate yourself. Audit actions: login, login_failed, login_locked, logout, permission_denied, change_password, password_change_failed, create_user, change_user_role, deactivate_user, activate_user, reset_user_password, start_camera, stop_camera; `user` = the username (typed name for failed logins). `api.auth.now` is the clock (tests replace it).
- Schema versions: `app/db.py` `VERSIONS` (numbered steps, `PRAGMA user_version`, one `BEGIN IMMEDIATE` transaction, only adds). A database with data is copied to `<db folder>/backups/<name>-v<N>-<time>.db` first (before the write lock: SQLite's backup can't read through a connection holding it). Step 1: `users` (plus `must_change_password`, `failed_logins`, `locked_until`), `sessions`, `sites` (one default: `DEFAULT_SITE_NAME`, `DEFAULT_SITE_TIMEZONE` "local"), `cameras.site_id` (nullable for SQLite, filled with the default site; `upsert_camera`/`ensure_cameras` set it). `db.connect(path, migrate=False)` skips the checks (the API checks once per file, then one cheap connection per request). Camera start/stop endpoints: `GET /api/cameras` (cameras:read), `POST /api/cameras/{name}/start|stop` (cameras:control; busy = 409).
- API data endpoints (Phase 3): every endpoint has a pydantic response model; operation ids = function names (`generate_unique_id_function`), all unique, for the frontend's generated TypeScript. Lists return `Page[T]` (items, total, page, page_size) with `page`, `page_size` (max 500), `sort` (field, "-" = descending; unknown field = 422), `q` and, for rows that belong to a site, `site_id` (`api/paging.py`: in memory for people/cameras/attendance/users/sites, SQL for events and audit). Site scope: attendance, people and overview by the person's site (`persons.site_id`), events and cameras by the camera's site; users, sites and audit are global (no site_id). `/api/attendance` and `/api/overview` use `app.db.day_summaries` (pure; `refresh_daily` and the reports use it too), so they match the old Streamlit Today page (verified in Edge on a copy of the real database). Corrections (`POST /api/attendance/corrections`, attendance:correct = hr, admin): add (person, direction or camera, time), change (keeps `original_timestamp` = the time before the first correction), void, restore; future times refused. Snapshots `/api/snapshots/{event_id}` and photos `/api/people/{id}/photos/{file}` only for logged-in users, paths confined to `data/` and the person's folder. Re-enroll uses `app.state.face_models` (lazy `Detector`, `Recognizer`; injectable). Cameras by DB id; the list is `cameras.json` (`camera_settings`), id/site from the cameras table; `public_source` keeps `${VAR}` placeholders and masks typed-in passwords; a Hikvision `password` goes to .env only; ROI (`camera_settings.check_roi`, fractions) is stored but not applied by the worker yet. `POST /api/cameras/test` refuses a running camera and a busy webcam; returns width, height, fps (reported), codec. Sites CRUD (sites:manage, admin; list sites:read, all roles); a site with cameras or people, or the last one, can't be deleted. Settings: `config.EDITABLE_SETTINGS` (thresholds, quality, vote, `COOLDOWN_SECONDS` = debounce, fps) with ranges; changes saved as overrides in `settings.json` (`config.SETTINGS_FILE`, `GATESENSE_SETTINGS_FILE`, git-ignored), applied at config import (`load_settings`, `refresh_settings`); workers read them at start; every change audited (`change_settings`, old/new). Tests reset settings to `DEFAULT_SETTINGS` (conftest). Schema step 2: `persons.site_id`, `attendance_events.original_timestamp`. Step 3: `user_preferences` (user_id, key, value, updated; `Database.preference`/`set_preference`). `FrameSource` fills codec/fps from a connection that ended before being announced (very short files).
- API live (Phase 4, `api/live.py`, `api/routes/live.py`): `GET /api/cameras/{id}/stream` (MJPEG, boundary `frame`, live:view = admin/hr/guard, 409 if stopped, ends when the worker stops, `max_frames` optional) and `/snapshot.jpg`. Workers are other processes, so frames go through `data/live/<camera>.jpg` as before: while anyone streams, the API's per-camera `Channel` thread touches `<camera>.watch` every second (`live.mark_watched`; fresh = `STREAM_WATCH_SECONDS`), and the worker's `LiveWriter.watched()` (checked twice a second) writes every processed frame up to `STREAM_FPS` and the `Pipeline` draws the view from the full frame at up to `STREAM_MAX_WIDTH` (boxes scaled from the detection copy). The channel reads each new file once (re-encodes only if wider than `STREAM_MAX_WIDTH`) and every viewer gets the same bytes, at most `STREAM_FPS`; with the last viewer the thread stops and the .watch file is deleted, so the worker is back to `LIVE_FRAME_SECONDS` at detection size. WebSocket `/api/ws`: `auth.websocket_user` (cookie session not extended, active, no pending password change, attendance:read; Origin must be the API itself or `API_CORS_ORIGINS`; refused with 1008 before accept); messages hello, event (new `attendance_events` rows, workers' or manual), camera (every `WS_CAMERA_SECONDS`: id, name, status, fps, error, warning, held_by, last_frame_at), attendance_changed (new audit rows add/edit/void/restore_event, so corrections made outside the API too). One `EventHub.run` task (lifespan) polls every `WS_POLL_SECONDS` only while clients are connected, starting from the newest ids; sessions are re-checked with the camera tick (ended = close 4401); each client has an `asyncio.Queue(WS_QUEUE)` in its own loop (`call_soon_threadsafe` from another loop: TestClient gives each client its own), a full queue drops that client (1013).
- Web dashboard (Phases 5-6, `web/`): Vite 8 + React **18.3.1** + TypeScript strict (`noUncheckedIndexedAccess`), Tailwind 4 (`@tailwindcss/vite`, tokens as CSS variables in `src/index.css` for light/dark: slate, teal accent #0E7C66, IN blue, OUT orange, status inside/left/missing/absent; 14 px body, tabular numbers, 8 px grid, 1 px bordered cards), shadcn/ui-style components written by hand with `forwardRef` (React 18 drops `ref` on plain function components, which breaks Radix `asChild` and react-hook-form `register`; the dialog overlay needed it too), Inter via @fontsource-variable (no Google request), TanStack Query/Table, react-router 7, react-hook-form + zod 3 (`@hookform/resolvers` 5: 6.0 has a peer conflict), Recharts, lucide-react, sonner, cmdk. All versions exact in `web/package.json`. Types: `npm run gen:api` (openapi-typescript 7 from the running API, `--default-non-nullable false` so request fields with server defaults stay optional) -> `src/api/schema.d.ts` (committed); `src/api/client.ts` typed by path/method (query, path params, JSON body, success type), `credentials: "include"`, a 401 calls the unauthorized handler (main.tsx: forget the user, router to `/login?next=`) except for login/me; `postImage` for the enrollment frame check. Vite proxies `/api` (with `ws: true`) to 127.0.0.1:8000. `src/app/routes.tsx` is shared by the app and the tests (memory router); guards: RequireAuth (login, then forced password change), RequireLogin, RequirePermission (403 page); sidebar items by permission (`src/app/nav.ts`; Settings = any of settings/users/cameras/sites manage). `useLiveEvents` (one WebSocket in `LiveProvider`): backoff 1/2/4/8/15 s, reset on open, refetch attendance queries on event/attendance_changed and after a reconnect, cameras on a status change, stop on 4401 and re-ask /me. Live cameras: MJPEG `<img>` only for 1-2 tiles and full screen; 4/9 tiles poll `snapshot.jpg` at 2 fps (browsers allow 6 connections per host and each MJPEG keeps one). Enrollment wizard: details (new or existing person) -> one step per required `ENROLL_STEPS` entry (getUserMedia, raw frame to `POST /api/enrollment/check?step=` every 300 ms, one in flight, guide box green and Capture enabled only on ok; preview mirrored with CSS, boxes mirrored too) -> review (`/api/enrollment/review`) -> save (`/api/people/{id}/enroll`, reason); the camera is a `CameraAdapter` (tests inject one). Tests: Vitest 5 + Testing Library (client, guards, live hook, attendance filters, correction form, wizard); ESLint 10 + Prettier (tailwind plugin). Webcam claim: the wizard's capture steps `POST /api/enrollment/webcam` before opening the webcam (409 while a webcam worker runs), renew it every `ENROLL_CAMERA_RENEW_SECONDS` (20) and `DELETE` it when they close (also on `pagehide`, `fetch` with `keepalive`); claims live in `api.workers.WorkerManager` (`claim_webcam`, `release_webcam`, `webcam_claimed_by`, one lock with `start()`), lapse after `ENROLL_CAMERA_CLAIM_SECONDS` (90) unrenewed, block webcam workers and webcam connection tests, and aren't audited (no data changes). Also (the old Streamlit features): live decisions over the WebSocket (`decisions` messages, `live:decisions` = admin only), person edit, void/restore in the day drawer, photo-file upload (`POST /api/people/{id}/photos`, max 10, check_photo), delete one photo / all face data, camera delete/move/log (`/api/cameras/{id}/log`, `log.txt`), Reports (`/api/reports/daily|monthly`, `/{kind}/export?format=csv|xlsx`, audited `export_report`). API additions for it: `/api/enrollment/steps|check|review`, `/api/people/{id}/enroll` (enroll_guide.capture_photo/review/finish under the models lock, audited `enroll_person`), `/api/system` + `/api/system/backup` (SQLite online backup + gallery copy to data/backups, audited `backup`), `Person.photo_url`, `/api/attendance?department=`.
- Enrollment camera choice: the wizard asks "Which camera?" after Details when IP cameras exist (`config.ENROLL_IP_TYPES` hikvision/rtsp; `GET /api/enrollment/sources`, the user's last choice in `user_preferences` key `enroll_source`, set on a new webcam claim or camera session). IP camera: `api/enroll_camera.py` `EnrollCameras` (`app.state.enroll_cameras`, opener injectable via `create_app(enroll_opener=)`), `POST /api/enrollment/sessions` (open/renew like the webcam claim, lapse after `ENROLL_CAMERA_CLAIM_SECONDS`, one camera per user: another user's wizard = 409, the same user's newest wins), `DELETE .../sessions/{id}`, `.../stream` (MJPEG of the window, `ENROLL_PREVIEW_FPS`/`ENROLL_PREVIEW_WIDTH`), `.../check?step=` (evaluate on the full-resolution centred window, `ENROLL_IP_WINDOW` 0.5 of width and height, so the guide box and steps are the webcam's), `.../capture?step=` (that window as a JPEG data URL, 409 unless the newest frame passes; then the usual review/save, `PhotosSave.source` audited in `enroll_person`). Frames: a running worker's are shared (the API touches `data/live/<camera>.enroll` every second; `LiveWriter.full_frame` in `Pipeline.process` writes the raw frame to `<camera>.full.jpg` on a thread, at most `ENROLL_FEED_FPS`, deleted when the marker goes stale), otherwise the API opens the camera itself (`open_live`, Hikvision forced to the main stream 101, `${VAR}` expanded only in the API process) and the worker can't start meanwhile (`WorkerManager.camera_holds`, one lock with `start()`; the camera test refuses too); a shared worker that stops is replaced by the API's own connection. The preview of an IP camera isn't mirrored. Sessions aren't audited (no data changes).
- One app (Phase 8): `python -m api.run` serves the API and the built dashboard (`web/dist`, `config.WEB_DIST`, `GATESENSE_WEB_DIST`) on one port (`api/web.py`: `/assets` cached immutable, any non-`/api` path -> `index.html` no-cache, `/api/...` stays JSON 404, no build -> 503 page; the catch-all is mounted last and hidden from OpenAPI). `GATESENSE_HOST` (default 127.0.0.1) / `GATESENSE_PORT` (8000); a host other than this PC needs `GATESENSE_SSL_CERTFILE` + `GATESENSE_SSL_KEYFILE` (uvicorn TLS; `config.HTTPS` makes the cookie Secure and adds HSTS) or `GATESENSE_ALLOW_HTTP=1` (warning). `api.run --preflight` (start.bat): already running (3, opens browser), HTTPS check, first start needs the admin password, port, web build missing/stale -> `npm ci`/`npm run build` (`web.build_status` compares web/ sources with dist/index.html; no Node.js = use the old build, or fail if none). The running app watches `data/run/_api.stop` (`stop.py`/stop.bat: workers, then the app) and `--open` opens the browser. `api/security.py` (pure ASGI, streaming untouched): CSP (self only; inline style attributes allowed; `/docs` and `/redoc` get a CDN-allowing policy), X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy (camera self), COOP; `MAX_REQUEST_BYTES` 10 MB -> 413 (Content-Length or counted). Login rate limit per IP (`LOGIN_RATE_LIMIT` 10 per `LOGIN_RATE_WINDOW_SECONDS` 60, sliding, 429 + Retry-After, audited `login_rate_limited`; tests get a fresh generous limiter in conftest). `api/maintenance.py`: lifespan loop (first check after `MAINTENANCE_CHECK_SECONDS`, so never at start), nightly once a day at/after `BACKUP_HOUR` (a missed day caught up once): SQLite online backup + gallery to `<db folder>/backups/<name>-nightly-<time>`, prune nightly ones after `BACKUP_RETENTION_DAYS` 14 (manual "Back up now" and pre-upgrade copies never), delete `snapshots/<day>/` older than `SNAPSHOT_RETENTION_DAYS` (30, an editable setting) and NULL those events' `snapshot_path` (events kept); audited as user `system`; last run in `data/run/_maintenance.json`, shown under Settings > System. `scripts/install_service.ps1`: NSSM service (base interpreter + `__PYVENV_LAUNCHER__`, `-m api.run --no-build`, Ctrl+C stop with 20 s, logs to data/logs/service.log, -Credential to run as the user: models live in the user profile; untested here: needs admin + nssm.exe).
- API database: `api/db.py` `Database` is the API's only data access; backend from `config.DATABASE_URL` (env `GATESENSE_DATABASE_URL`; None = SQLite at `DB_PATH`), SQLite reuses `app.db`. `postgresql://` is recognised and refused ("not supported yet"); PostgreSQL needs a backend there plus porting `app.db` (the workers use it too).
- First admin password: `GATESENSE_ADMIN_PASSWORD` (`config.DASHBOARD_PASSWORD_ENV`), read from the environment or from `.env` in the project root (python-dotenv, `override=False`, so a real environment variable wins), via `app/env.py` (`admin_password_source`, used by `api.run --preflight` and `api.auth`). Never hard-code, print or log it; only say where it was found. No users yet and no password = refuse to start. `.env` is git-ignored; `.env.example` is the template. Tests never read the real `.env` (see `tests/conftest.py`).
- Corrections never delete: add manual events, re-time, void/restore. Every change (events and people) needs a reason and writes `audit_log` in the same transaction. Exception: enrollment (adding a person, the wizard's save, photo files) asks no reason; `api.schemas.OptionalReason` audits a default ("added for enrollment", "guided enrollment", "enrollment photos from files") unless one is sent.
- `enroll.py` adds new people and deactivates removed ones (folder gone from known/), but never re-activates someone an admin deactivated. People added on the dashboard with no photos yet are not deactivated.
- Enrollment photo rules all live in `app/enroll_quality.py` (`check_photo(image, detector) -> QualityResult`: ok, plain `reason`, short `short`, `code`, score 0-100, yaw/pitch in degrees, face_px, blur, det_score, brightness). Order: readable, face found (detector at `ENROLL_DET_THRESHOLD` 0.4), one face, size, in frame, brightness, yaw (`ENROLL_MAX_YAW` 35°), pitch (`ENROLL_MAX_PITCH` 25°), blur; pose before blur so turned faces get the actionable message. Pose comes from InsightFace's 3D-landmark model (`1k3d68.onnx`, `models.pose_model()`, `Detector.pose`), loaded only for enrollment; the 5-landmark estimate is a fallback only (it was off by up to 15° on real photos). The live cameras keep `detector.check_quality` (ratio-based) and the 0.45 / 0.05 match settings. Per-photo results are in `known/<code>/photos.json` (written by `enroll_one`/`enroll_all`, read by the API's person profile so it needn't run models just to show photos).
- Guided enrollment: `app/enroll_guide.py` (no web framework: steps from `config.ENROLL_STEPS`, `evaluate`, `final_check`, `guide_box`, `GuidedSession`, `capture_photo`, `review`, `finish`), served by `api/routes/enrollment.py` to the React wizard. Yaw convention: + = the person's own left; InsightFace yaw on a raw (unmirrored) image is + when the nose points to the image's right, which is the person's left; all frames (the browser's camera, OpenCV) are raw, only the preview is mirrored. Finish writes the step into `photos.json` (`write_sidecar(..., extra)`, `KEEP` fields survive rebuilds).
- Enrollment logic lives in `app/enrollment.py`, shared by `enroll.py` (full rebuild) and the API (per-person rebuild: wizard, photo upload, delete photo). Folder name = employee code. Delete face data removes photos + embeddings, keeps attendance, needs a reason, is audited.
- Workers: the app (Live cameras page, `POST /api/cameras/{id}/start`) runs `recognize.py --camera NAME --no-window --parent-pid <app pid>` via `app/workers.py`. Protocol: status `data/run/<camera>.json`, clean stop via `data/run/<camera>.stop`, log `data/logs/<camera>.log`. Workers exit if the app dies (stop reason "GateSense exited"); a hard kill is only a fallback and only for workers this process started. On Windows, launch the base interpreter with `__PYVENV_LAUNCHER__` (`workers.python_command`), as multiprocessing does, because the venv `python.exe` is a launcher with a child process. Same-webcam workers and duplicate workers per camera are refused (app and CLI). Workers reload `gallery.npz` when it changes; the gallery is saved atomically.
- RTSP (`rtsp://`, e.g. Hikvision): `app/frame_source.py` `FrameSource`, chosen by `frame_source.open_live()`. FFmpeg backend, `OPENCV_FFMPEG_CAPTURE_OPTIONS` = `RTSP_FFMPEG_OPTIONS` (TCP, 5 s timeout; an existing env value wins), open/read timeouts 5000 ms. Newest frame only; reconnects forever with `RTSP_RECONNECT_BACKOFF` (1, 2, 4, 8, 16, 30 s; resets after a working connection) on open failure, read failure, no frame for `RTSP_STALE_SECONDS`, or no first frame within `RTSP_CONNECT_GRACE_SECONDS`. A stale connection is abandoned (its daemon thread releases the capture when the read returns), never joined. It never ends the worker. Health (state, size, input/processed fps, last frame time, reconnects today, last error, live since) goes into the worker status file (`health`) and the camera's status in the API. Mask passwords with `camera.mask_source` everywhere: logs, status, `cameras.source` in the DB, log tails, dashboard.
- Camera passwords never go in `app/config.py`: sources use `${VAR}` placeholders (`app/sources.py`), looked up in the environment, then `.env` (read fresh with `dotenv_values`, not loaded into `os.environ`). Values in the URL's `user:password@` part are percent-encoded (FFmpeg decodes them; verified). Expand only where a stream is opened (`recognize.run`, `probe_camera.main`); the dashboard, status, DB and logs keep the placeholder form. Missing/empty variable: `WorkerManager.start` refuses, the Live cameras page shows the error, the worker exits with reason `missing environment variable X`. `GATESENSE_ENV_FILE` overrides the `.env` path (tests).
- Camera list (`app/camera_settings.py`, edited in Settings > Cameras through `/api/cameras`): cameras in `cameras.json` (`config.CAMERAS_FILE`, override `GATESENSE_CAMERAS_FILE`; replaces `DEFAULT_CAMERAS` when present; no passwords; git-ignored as site-specific, `cameras.example.json` is the committed template). `config.refresh_cameras()` runs on camera requests so hand edits/deletion apply without a restart; with no file, `entries()` shows `DEFAULT_CAMERAS`. Check UI changes in a real browser (Playwright driving the installed Edge from a scratch venv), not only the unit tests. Types webcam / hikvision (URL built from IP, port, user, channel, main=01/sub=02) / rtsp (URL must use `${VAR}` for a password, typed passwords refused) / file. Hikvision passwords are written to `.env` as `GATESENSE_CAM_<NAME>_PASS` with python-dotenv `set_key` (other lines kept, verified by reading back) and never displayed. Running cameras can't be edited/deleted; names are fixed; changes audited via `db.log_change` (no passwords in details). `.env` is never loaded wholesale into the app's environment (`env.load_env` copies only the admin password), otherwise workers would inherit stale camera passwords that win over `.env` edits.
- Webcams (and other URLs) keep `camera.LiveCapture`; video files keep in-order reading. Don't route them through `FrameSource`.
- Live sources (webcam, RTSP) are read on a background thread (`camera.LiveCapture`, newest frame only) so a hung or busy camera never blocks status/Stop; `live.CameraHealth` warns on no frames or black frames (a webcam held by another app opens fine but gives 1 fps black frames, or blocks). Video files are still read in order on the main thread. `recognize.Pipeline.process()` is shared by both loops.
- Live view: workers write `data/live/<camera>.jpg` (the already-processed, annotated frame) and `<camera>.json` (fps, frame time, last 20 decisions) at most every `LIVE_FRAME_SECONDS`, atomically (`app/fileutil.py`); deleted on stop (the manager deletes them for a killed worker). No extra detection for the view.
- `start.bat` / `stop.bat` (CRLF, kept by `.gitattributes`): start.bat runs `api.run --preflight` (0 ok, 1 can't start, 3 already running → opens browser), then `api.run --open --no-build` in a minimized window. `stop.bat` runs `scripts/stop.py`: stop files to every live worker (any starter), then `data/run/_api.stop`; it never kills. Use `ping` for delays in batch files, not `timeout` (fails without an interactive console).
- `GATESENSE_DATA_DIR` overrides `data/` (used for isolated runs). Tests never touch the real `known/`, `data/` or `.env` (`tests/conftest.py`).
- Next phase: night-shift windows. Later: PostgreSQL, liveness check, Docker.

## Folder layout

```
app/

  env.py         loads .env (never overrides real environment variables)
```

## How to run

All commands from the project root, using the venv:

```
.venv\Scripts\python scripts\check_env.py                  # environment + webcam check
.venv\Scripts\python scripts\enroll.py                     # build gallery from known/
.venv\Scripts\python scripts\enroll.py --capture waqas     # capture webcam photos, then build
.venv\Scripts\python scripts\recognize.py                                  # entrance (webcam, IN)
.venv\Scripts\python scripts\recognize.py --camera exit --source clip.mp4  # exit (OUT) from a clip
.venv\Scripts\python scripts\recognize.py --no-db                          # tune without recording
.venv\Scripts\python scripts\today.py                                      # today's attendance
.venv\Scripts\python -m app.probe_camera entrance                          # check a camera's picture (20 s)
start.bat / stop.bat                                                       # start / stop everything (double-click)
cd web && npm install && npm run dev                                       # React dashboard on http://localhost:5173 (API must run)
.venv\Scripts\python -m api.run                                            # API on 127.0.0.1:8000 (or start-debug.bat)
.venv\Scripts\python -m pytest                                             # Python tests (cd web && npm test for the web app)
```

`recognize.py` logs one line per match decision (time, track, name or unknown, score, second-best score, verdict) for threshold tuning, plus a line per event or cool-down skip.

## Rules

- **Build one phase at a time** and wait for the user's OK before starting the next.
- **Never commit face images or embeddings.** `known/`, `data/`, `*.npz` and image files are git-ignored; keep it that way.
- **Don't run `git commit`** at all; the user commits everything themselves.
- **Keep thresholds and camera settings in `app/config.py`.** Don't hard-code them in other modules. Cameras are edited in Settings > Cameras and saved to `cameras.json`, but `config.CAMERAS` (loaded by `config.load_cameras()`) stays the only place the rest of the code reads them from.
